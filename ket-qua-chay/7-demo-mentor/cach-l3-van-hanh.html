Cách L3 Generator chạy

Trang này giải thích bằng lời thường: công cụ làm gì, chạy qua những bước nào, và mỗi thông tin trên màn hình lấy từ đâu. Ví dụ lấy từ repo teamhide.

Công cụ làm gì, trong 4 câu

  1. Bạn đưa vào code của một dự án Python dùng FastAPI, dạng file ZIP.
  2. Công cụ đọc code và viết ra tài liệu: danh sách API, các bảng dữ liệu, các sự kiện.
  3. Mỗi thông tin trong tài liệu đều chỉ ra được nó lấy từ file nào, dòng nào.
  4. Công cụ chỉ đọc. Nó không chạy code, không sửa code. Phần này không dùng AI.

Nói:Công cụ đọc code, ghi lại từng thông tin kèm dòng code, tự kiểm lại, rồi mới viết tài liệu.

Sáu bước chạy

Mỗi lần gửi một repo, công cụ đi qua 6 bước theo thứ tự. Bước 4 là phần của Khiêm.

  1. 1Nhận fileMở ZIP, chặn file nguy hiểm, lấy mã hash từng filesnapshot.py
  2. 2Chọn fileGiữ file Python và file khai thư việnsnapshot.py
  3. 3Đọc codeTìm API, bảng, cấu hình, thư viện…pyindex.py, extract.py
  4. 4 · KhiêmChia khốiGom file thành các khối. Demo này chia tạmmodel.py
  5. 5Tự kiểmSo từng thông tin với đúng dòng codeverify.py
  6. 6Viết tài liệuViết file, đọc lại để chắc ghi đúngrender.py

Mã hash là một chuỗi ký tự tính từ nội dung file. File đổi dù một chữ thì mã cũng đổi. Công cụ dùng nó để biết file có bị sửa sau khi đã đọc hay không.

Nói:Không bước nào của phần này dùng AI. Vì vậy chạy lại bao nhiêu lần cũng ra cùng một kết quả.

Công cụ ghi lại những gì

Làm sao biết công cụ không bịa

Mỗi giá trị đi kèm một bằng chứng: tên file và số dòng. Ở bước 5, công cụ tự kiểm 3 điều cho từng giá trị:

  1. File đó đúng là file đã nhận và chưa bị đổi. Công cụ so mã hash để biết.
  2. Số dòng có thật trong file.
  3. Giá trị nằm nguyên văn ở các dòng đó. Ví dụ với đường dẫn đăng nhập, công cụ phải thấy chữ /api/v1/user ở file 1 và chữ /login ở file 2.

Sai một điều thì giá trị bị xóa, ô đó chuyển sang "chưa biết" kèm lý do.

Trên web, bấm nút file:dòng là thấy đúng đoạn code đó. Nếu file đã bị sửa sau khi phân tích, web báo thay vì hiện code mới.

Nói:Trên 4 repo có 4.400 bằng chứng. Máy kiểm cả 4.400, tất cả đều đúng.

Chắc chắn đến đâu

Có giá trị đọc thẳng từ code. Có giá trị phải suy ra theo quy ước của FastAPI. Ví dụ code không ghi status thì FastAPI mặc định trả 200. Công cụ vẫn ghi 200, nhưng đánh dấu là "suy ra" và ghi tên quy ước đã dùng.

Chữ trong file kết quảNghĩa
exactĐọc thẳng từ code
inferredSuy ra theo một quy ước có tên
fullMọi ô đều đã biết
partialCòn ô chưa biết

Quy định: thứ phải suy ra không bao giờ được ghi là "đọc thẳng". Trên web, cột "Độ chắc chắn" viết điều này bằng chữ, ví dụ "suy ra: status".

Chưa làm, hoặc cố ý không làm

  • Không đoán auth. Chưa có quy tắc. Đoán sai nguy hiểm hơn để trống.
  • Không viết lệnh tạo bảng khi chưa biết loại database.
  • Mới đọc được một ứng dụng trong mỗi repo.
  • Nhận repo từ GitHub: đã có code, đang tắt chờ kiểm tra bảo mật.
  • Chia khối: phần của Khiêm, chưa chọn cách chia.
  • Chưa chấm điểm chính thức. Xem mục "Đang vướng ở đâu".

Nhóm đang vướng ở đâu, và làm gì tiếp

Phần đọc code và viết tài liệu API, bảng dữ liệu đã chạy được. Phần vẽ sơ đồ kiến trúc chưa xong. Và nhóm chưa có bài kiểm tra công bằng để nói "đạt".

1Chưa chọn cách chia code thành các khối

Chuyện gì: Muốn vẽ sơ đồ, công cụ phải gom file thành từng khối (component), ví dụ khối "người dùng", khối "đăng nhập". Có 3 cách gom đang được cân nhắc, nhóm chưa chọn cách nào. Hai tài liệu của nhóm còn ghi khác nhau về việc này.

Vì sao là vấn đề: Chưa có khối thì chưa có sơ đồ. Tài liệu API cũng phải xếp theo khối, nên hiện đang để tạm một khối tên APP.

Làm gì: Thử cả 3 cách trên cùng 4 repo, so với đáp án làm bằng tay, chọn cách tốt nhất rồi ghi lại.

Mã trong tài liệu: D-03, FR-022

2Chưa có tài khoản AI miễn phí

Chuyện gì: PRD quy định chỉ dùng AI miễn phí (Groq, Gemini). Nhóm chưa có tài khoản này. Thí nghiệm của Khiêm đang dùng OpenAI, loại trả phí.

Vì sao là vấn đề: Kết quả đang có không chạy đúng điều kiện PRD đặt ra.

Làm gì: Đăng ký tài khoản miễn phí rồi chạy lại. Nếu bản miễn phí không đủ dùng, xin mentor cho phép trả phí.

PRD dòng 173

3Chưa có bài kiểm tra công bằng

Chuyện gì: Muốn nói "công cụ đúng 80%", phải thử trên repo công cụ chưa từng thấy. 4 repo hiện tại là repo nhóm đã dùng để sửa lỗi. Số lượng cũng còn ít: cần ít nhất 100 route mà mới có 58; cần 20 bảng mà mới có 5.

Vì sao là vấn đề: Con số đẹp trên 4 repo này chưa chứng minh được công cụ chạy tốt với repo mới. Giống chấm điểm bằng chính đề đã ôn.

Làm gì: Tìm thêm 4–6 repo mới và khóa lại, không dùng để sửa lỗi. Người làm đáp án phải khác người viết phần đó.

OBS-L3GEN-001, 5 KPI

4Giấy tờ đi sau việc làm

Chuyện gì: Theo quy trình, phải ký duyệt phạm vi rồi mới làm. Nhóm đã viết code nhưng chưa ký. PRD chưa ghi ngày cho các mốc. Nhiều file chưa lưu vào git.

Vì sao là vấn đề: Mentor không biết bản nào là bản chốt, và không biết nhóm đang trễ hay đúng hạn.

Làm gì: Trong tuần này: Khiêm ký duyệt, ghi ngày cho các mốc, rồi lưu các file vào git.

Scope Gate, PRD mục VIII và IX

5Hai phần chưa ghép với nhau

Chuyện gì: Hoàng làm phần tài liệu API và bảng. Khiêm làm phần chia khối. Hai phần nằm ở hai nơi. Hôm nay mới ghép bằng tay qua một file ghi "file nào thuộc khối nào".

Vì sao là vấn đề: PRD muốn mọi đầu ra sinh từ cùng một kết quả phân tích.

Làm gì: Dùng chính file đó làm chỗ nối cố định. Khiêm xuất file theo đúng mẫu, Hoàng cho công cụ tự đọc.

File membership, AC-025-04

6Tài liệu API còn vài chỗ trống

Chuyện gì: Repo chứa nhiều ứng dụng thì mới đọc được một. Chưa biết repo dùng loại database nào, nên chưa viết được lệnh tạo bảng. Chưa biết API nào cần đăng nhập. Chưa đọc được Celery.

Làm gì: Làm trước việc đọc nhiều ứng dụng, vì PRD xếp mức bắt buộc. Sau đó đọc loại database từ chuỗi kết nối trong cấu hình, ví dụ postgresql://.
