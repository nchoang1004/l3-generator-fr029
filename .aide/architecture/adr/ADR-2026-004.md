# ADR-2026-004 — Chia component của repository được phân tích theo contract

- **Trạng thái:** draft. Khiêm chọn hướng "lần theo contract" ngày 02/10/2026 ([CR-L3GEN-2026-004](../../evidence/requests/CR-L3GEN-2026-004.yaml)). Hướng này đã vào [FR-L3GEN-028](../../requirements/fr/FR-L3GEN-028.md) revision 3 và qua Scope Gate. ADR ghi lý do và các phương án đã thử. Chưa ký Architecture Gate.
- **ADR này viết sau khi đã quyết.** Nó ghi lại một quyết định đã có, không phải để chọn lại. Tiêu chí ở mục 3 lập lúc viết ADR, sau khi đã thử A, B, C và đã chọn D.
- **Revision 2 (02/10/2026):** sửa theo review REVIEW-ARCH-L3GEN-2026-001 (A6, A7, A11, A12): nói rõ ADR viết sau quyết định; bỏ chữ "đạt" chưa có số đo; dẫn nguồn số đo; nêu file v7 còn dùng.
- **Khác ADR-2026-003:** [ADR-2026-003](ADR-2026-003.md) chia component của chính công cụ. ADR này nói công cụ chia component cho repository nó phân tích.

## 1. Vấn đề

Công cụ đọc một repository FastAPI và phải chia file của repository đó thành component. Cùng một cách chia dùng cho hai đầu ra: sơ đồ ([FR-L3GEN-028](../../requirements/fr/FR-L3GEN-028.md)) và thư mục `tech-specs/<component>/` ([FR-L3GEN-029](../../requirements/fr/FR-L3GEN-029.md) đến 031).

Từ 24/09 đến 01/10/2026 dự án chia theo tầng: Điểm vào, API, Nghiệp vụ, Dữ liệu, Hạ tầng. Ngày 02/10 Khiêm thấy đó là chuẩn dự án tự đặt. Quy trình mentor (EXEC mục A.1, Đề bài 3.6) định nghĩa khác: component gánh một trách nhiệm nghiệp vụ và sở hữu contract API, TBL, EVT; route, service, repository, model là cấu trúc bên trong component. Chia theo tầng thì route nằm ở khối "API", bảng nằm ở khối "Dữ liệu", nên không khối nào sở hữu trọn contract của một nghiệp vụ.

## 3. Tiêu chí quyết định

Lập khi viết ADR, sau khi đã chọn D. Tiêu chí 1 lấy từ định nghĩa của mentor, mà D được dựng theo định nghĩa đó. Vì vậy tiêu chí 1 là lý do chọn, không phải kết quả so sánh.

| Tiêu chí | Cách đánh giá |
|---|---|
| Đúng định nghĩa mentor | Component sở hữu trọn contract của nó; thư mục `tech-specs/` trùng khối trên sơ đồ |
| Code quyết phần chắc | Không có model, code vẫn cho mỗi file một component, mỗi contract một chủ; cùng đầu vào cùng kết quả |
| Model chỉ làm phần code không quyết được | Mỗi quyết định của model có mã dòng; code kiểm được; nằm trong trần chi phí |
| Luật chung | Không có tên hay luật riêng cho một repository |
| Đo được | Có đáp án theo đúng định nghĩa và có P/R trên repository kín nhỏ, vừa (KPI-L3GEN-006) |

## 4. Các phương án

Số đo của A, B, C chấm theo đáp án chia theo tầng (bản 4, 8 repo). Đáp án đó không theo định nghĩa mentor, nên các số này **không so thẳng được** với D. Chúng cho biết phần đường ống (cách đưa dữ liệu vào model, cách lấy bằng chứng ra) chạy tốt tới đâu; D dùng lại phần đường ống đó.

### Phương án A — Chia theo thư mục

Model đọc danh sách thư mục rồi chia khối (v3 đến v6, 24–28/09). Bản vá 28/09: code chia theo thư mục, model gộp hoặc tách.

| | |
|---|---|
| Được | Đơn giản. Ổn ở repository nhỏ có thư mục theo tính năng |
| Mất | Thư mục không trùng trách nhiệm: repository xếp thư mục theo tầng (`api/`, `models/`, `crud/`) cho ra component theo tầng. Repository lớn: danh sách thư mục bị rút gọn cho vừa trần token, model bịa đường dẫn, bỏ sót file (fba v6: 114/226 file không được xếp). Bản vá thua ở 6/6 repository. Nguồn: `evaluation/quote-evidence/runs/v6-fba/`; quyết định 28/09/2026 ở `docs/HANDOFF.md` mục 3 |

Trượt tiêu chí "đúng định nghĩa mentor".

### Phương án B — Chia theo tầng, model chốt khối (v8)

Code dựng bản nháp từ dữ kiện; model đọc bản tóm tắt toàn repository và trả danh sách khối theo tầng, kèm mã dòng; code kiểm luật gộp (30/09).

| | |
|---|---|
| Được | Số tốt nhất trên đáp án theo tầng: 4/4 repository nhỏ đạt P ≥ 0,8, R ≥ 0,6; kibo đạt. Mọi bằng chứng do model trỏ đều hợp lệ ở repository nhỏ. Dưới 0,003 USD mỗi repository nhỏ |
| Mất | Khối là tầng, không phải component sở hữu contract. Repository vừa, lớn chưa đạt: boilerplate P 0,62; lnbits R 0,50; fba R 0,29 |

Trượt tiêu chí "đúng định nghĩa mentor".

### Phương án C — Tóm tắt từng file rồi ghép, kiểu ArchAgent và SemRef (v9)

Model phân loại thư viện, tóm tắt từng file; code chia cụm Louvain; model ghép cụm theo tầng và sửa tối đa 3 lượt (01/10).

| | |
|---|---|
| Được | Theo hướng của các paper có số đo tốt nhất tìm được |
| Mất | Kém B ở 6/6 repository chạy xong. Ví dụ P/Pk/R: boilerplate 0,17/0,14/0,09 (B: 0,62/0,48/0,91); rhoboro 1,00/0,67/0,50 (B: 1,00/0,80/1,00). Lỗi chính là cài đặt: tóm tắt bị cắt vì trần trả lời, model phân loại thư viện sai. Tốn 835.761 token, tính tới lúc dừng (kibo, lnbits chạy dở). Mục tiêu vẫn là khối theo tầng. Nguồn: `evaluation/quote-evidence/runs/v9-*` |

Trượt tiêu chí "đúng định nghĩa mentor" và "model chỉ làm phần code không quyết được".

### Phương án D — Lần theo contract (chọn)

Code liệt kê contract (route, bảng, tác vụ nền), lần theo lời gọi từ mỗi route xuống tới mức tên cấp cao nhất (hàm, lớp, biến), lập nhóm route theo file khai báo, xếp tên và file vào nhóm theo luật "Cách xếp file" của FR-L3GEN-028. Model gộp các nhóm route cùng trách nhiệm, đặt tên, viết một câu trách nhiệm và chọn tên dùng chung chỉ một component dùng; mỗi quyết định trỏ mã dòng; code kiểm.

| | |
|---|---|
| Được | Đúng định nghĩa mentor theo cách dựng: component bắt đầu từ contract nó sở hữu. Không có model vẫn chia được (tên theo đường dẫn). Model không tách nhóm, không thêm mũi tên. 5 repository nhỏ: 7 request, khoảng 25.000 token, 0,008 USD. 7 repository (0 token): tập route trên sơ đồ bằng tập route trong `tech-specs/` ở 6/7 repository. Nguồn: `evaluation/quote-evidence/runs/contract-v1/`, `runs/l3gen-v1/` (chưa commit) |
| Mất | **Chưa có P/R**: chưa có đáp án theo định nghĩa này. Điểm yếu đã thấy khi tự đọc kết quả (chưa đo): file chứa bảng của nhiều component rơi vào "Dữ liệu dùng chung" vì xếp theo file; `session.get(...)` bị hiểu là gọi vào file khai session; teamhide còn 11 file "Chưa xếp"; model gộp notebooks và notes của rhoboro thành một (tranh cãi được) và tạo component cho container DI của teamhide. Repository có ít route thì phần lớn file không được nhóm route nào đi tới |

Tiêu chí 1 và 2 đạt theo cách dựng, chưa có số đo: tập route khớp ở 6/7 repository; bảng của nhiều component có thể nằm ở "Dữ liệu dùng chung" (FR-L3GEN-028 cho phép); chưa đo cùng đầu vào có cho cùng kết quả không. Tiêu chí 3, 4 đạt theo thiết kế (NFR-L3GEN-AI-002, luật chung). Tiêu chí 5 chưa đạt.

## 5. Quyết định

Chọn **phương án D**. Khiêm chọn hướng ngày 02/10/2026; luật chi tiết ở FR-L3GEN-028 revision 3 (đã duyệt ở Scope Gate).

Lý do: chỉ D dựng component từ contract nó sở hữu, nên sơ đồ và `tech-specs/` dùng chung một cách chia mà không phải ánh xạ. A, B, C có thể đạt số cao hơn trên đáp án cũ, nhưng đáp án cũ đo một thứ khác.

D dùng lại từ B: dữ kiện lời gọi của code, luật mũi tên chỉ vẽ luồng, mã dòng thay cho chép code, code kiểm câu trả lời của model.

## 6. Hệ quả

- Đáp án sơ đồ bản 4 (theo tầng) không dùng để nghiệm thu nữa. Cần đáp án mới theo định nghĩa mentor, do subagent viết mù, Khiêm duyệt. KPI-L3GEN-006 chặn nghiệm thu FR-L3GEN-028 tới khi đạt (PRD mục VIII).
- Chia component là việc của [CMP-L3GEN-005](../l2/CMP-L3GEN-005.md). [CMP-L3GEN-008](../l2/CMP-L3GEN-008.md) dùng cùng cách chia cho sơ đồ và `tech-specs/`, không tự gán lại chủ contract.
- Model chỉ nhận nhóm route, tên dùng chung và các dòng mang mã ([CMP-L3GEN-006](../l2/CMP-L3GEN-006.md)); không nhận nguyên file.
- Code v6 đến v9 ở `experiments/quote-evidence/` giữ làm lịch sử, không nằm trên đường chạy của sản phẩm. Ngoại lệ: `contract_llm.py` còn dùng lớp `Lines` của `ai7.py` (v7, kéo theo `flow.py`, `draft.py`, `graph.py`) và `verify.py` (lệch 005-8 ở [CMP-L3GEN-005](../l2/CMP-L3GEN-005.md)).

## 7. Phần không làm

- Repository mà phần lớn file không nhóm route hay tác vụ nền nào đi tới.
