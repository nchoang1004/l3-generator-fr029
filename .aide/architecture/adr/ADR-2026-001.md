# ADR-2026-001 — Mức trừu tượng của kết quả: phân tích sâu, trình bày ở L3

- **Trạng thái:** draft. Scope và ngưỡng 500/50 đã chốt qua OQ-L3GEN-002/004; ADR vẫn chờ Architecture Gate sau Scope Gate.
- **Ngày soạn:** 2026-09-16.

## 1. Vấn đề

Công cụ phải chứng minh được quan hệ kiến trúc bằng source. Muốn chứng minh, engine phải đọc khá sâu: tham số hàm, dependency injection, thuộc tính của đối tượng, chuỗi lời gọi. Ví dụ để kết luận `Orders API → Order Service → Order Repository → bảng orders`, engine phải đi qua `create_order()` → `get_service()` → `__init__()` → `create()` → `save()`.

Câu hỏi: những gì engine đọc được có nên hiện ra thành kết quả cho người đọc không?

Nếu có, một repository 500 function sinh ra sơ đồ 500 node. Người đọc không dùng được, và sản phẩm trượt từ bài toán sinh tài liệu kiến trúc sang bài toán dựng graph toàn repository — là phạm vi của một dự án khác trong đề bài (mục 3.8).

Nếu không, phải định nghĩa rõ ranh giới: cái gì là kết quả, cái gì là bằng chứng.

## 2. Ràng buộc

- Đề bài mục 3.6 yêu cầu đầu ra là tài liệu L3, component model và dependency diagram — không yêu cầu call graph mức function.
- Đề bài mục 3.8 là một dự án riêng về Repository Knowledge Graph. Không được lấn sang.
- Quan hệ chính phải có bằng chứng truy về source (NFR-L3GEN-TRACE-001). Không thể bỏ dữ liệu chi tiết đi.
- Timebox chương trình 4–6 tuần, team 2–3 người (PRD mục III.3).

## 3. Tiêu chí quyết định

Ghi trước khi xem phương án:

| Tiêu chí | Cách đánh giá |
|---|---|
| Trả lời được câu hỏi kiến trúc | Người đọc mới tìm được component, dependency, API, bảng dữ liệu mà không cần tác giả hướng dẫn |
| Giữ được bằng chứng | Mỗi quan hệ kiến trúc truy ngược được về file và dòng |
| Sơ đồ đọc được | Số node không tăng theo số function của repository |
| Đúng phạm vi đề bài | Không thực hiện phần thuộc mục 3.8 |
| Khả thi trong timebox | Không đòi hỏi phân tích toàn diện mọi cấu trúc động của ngôn ngữ |

## 4. Các phương án

### Phương án A — Chỉ phân tích ở mức component

Không đọc xuống mức function. Nhóm file theo thư mục hoặc package, suy dependency từ import giữa các package.

| | |
|---|---|
| Được | Đơn giản, nhanh, sơ đồ nhỏ |
| Mất | Không chứng minh được quan hệ. Import không đồng nghĩa có dùng. Không biết route nào chạm bảng nào |

**Bị loại.** Trượt tiêu chí "giữ được bằng chứng". Sơ đồ sinh ra sẽ đúng hình thức nhưng không kiểm chứng được — chính là vấn đề mà sản phẩm định giải quyết (PRD mục II.2).

### Phương án B — Phân tích sâu và trình bày hết những gì phân tích được

Đọc tới mức function, xuất toàn bộ node và cạnh ra sơ đồ, cho người dùng tự lọc.

| | |
|---|---|
| Được | Không mất thông tin. Một mô hình duy nhất, không phải chia lớp |
| Mất | Sơ đồ 500 node không đọc được. Phải làm graph query, traversal, incremental để lọc mới dùng nổi — tức là làm mục 3.8 |

**Bị loại.** Trượt tiêu chí "sơ đồ đọc được" và "đúng phạm vi đề bài". Việc lọc bị đẩy sang người dùng, trong khi lọc đúng mức chính là giá trị của sản phẩm.

### Phương án C — Phân tích sâu, trình bày ở L3, chi tiết giữ làm bằng chứng

Engine đọc sâu tới mức cần thiết để chứng minh. Kết quả chia hai lớp:

- **Lớp kiến trúc** (mặc định): application, component, hệ thống ngoài; quan hệ API, DB, external, event.
- **Lớp bằng chứng** (mở khi cần): code entities, chuỗi lời gọi, vị trí source đã tạo nên kết luận ở lớp trên.

| | |
|---|---|
| Được | Đạt cả năm tiêu chí. Sơ đồ nhỏ, kết luận vẫn kiểm chứng được |
| Mất | Phải định nghĩa và duy trì hai lớp dữ liệu; phải có quy tắc gộp nhiều cạnh code thành một dependency |

## 5. Quyết định

Chọn **phương án C**.

Nguyên tắc phát biểu ngắn: **phân tích đủ sâu, trình bày ở mức L3.**

Hệ quả cụ thể:

1. Node trong sơ đồ mặc định là application, component và hệ thống ngoài. Không có node cho mỗi function.
2. Nhiều lời gọi code giữa hai component gộp thành một dependency, kèm danh sách nguồn đóng góp.
3. Dữ kiện mức function/class vẫn nằm trong bộ kết quả, ở lớp bằng chứng có nhãn riêng.
4. Quan hệ chưa resolve được đích không trở thành cạnh kiến trúc. Nó ở lại lớp dữ kiện với nhãn unresolved và lý do.

## 6. Phần không làm

Quyết định này loại các mục sau khỏi phạm vi, không phải vì chúng vô giá trị mà vì chúng thuộc bài toán khác:

- Hiển thị mọi function/class trong sơ đồ L3.
- Call graph đầy đủ ở mức function như một đầu ra cho người đọc.
- Graph query API, graph traversal, incremental graph.
- Nối mọi tham chiếu trong repository, xử lý mọi kiểu factory/plugin/code động.
